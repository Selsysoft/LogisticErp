## 0. Özet ve kapsam sınırı

### 0.1 Terimler

- **Köken kaydı** (origin settlement): çeki doğuran ödeme/tahsilat. `settlement.instrument_id = çek` ve (`COLLECTION` + `RECEIVED`) ya da (`PAYMENT` + `ISSUED`).
- **Ciro kaydı**: `PAYMENT` + `RECEIVED` çek (`InstrumentService.endorse`). Aynı çekin birden çok ciro kaydı olabilir; en çok biri `POSTED` kalır, diğerleri düzeltme sonucu `REVERSED` olur.
- **Emanet kasası** (`custody_fund_id`): portföydeki çekin fiziken durduğu CASH fon. Para hareketi değildir (ZTO `TahsilKasaCiro` / "Kasaya Al (Ciro)").
- **Yaprak** (`check_leaf`): koçandaki tek çek kağıdı. Durumu `UNUSED` / `USED` / `VOID`.

### 1.1 `MIG/V37__instrument_extensions.sql` (Z08)

```sql
-- Z08 · Faz 12.3 · MX3 §2.1-§2.2, §4 (V22 taslağının yerine) · 12.3_TASARIM §1.1
-- Çek/senet ek alanları, emanet kasası, hareket fonu. Yeni durumlar (CANCELLED, RETURNED, COLLATERAL,
-- PROTESTED) yalnız Java'da: status VARCHAR(20), DB CHECK yok (V3).

-- 1. Bileşik FK hedefi (V38 check_leaf ve ileride kredi teminatı için)
ALTER TABLE instrument ADD CONSTRAINT instrument_id_company_uq UNIQUE (id, company_id);

-- 2. Ek alanlar
ALTER TABLE instrument
    ADD COLUMN issue_date      DATE,
    ADD COLUMN bank_branch     VARCHAR(100),
    ADD COLUMN drawer_name     VARCHAR(200),
    ADD COLUMN description     VARCHAR(500),
    ADD COLUMN custody_fund_id UUID,
    ADD COLUMN note_type       VARCHAR(20),
    ADD COLUMN is_collateral   BOOLEAN NOT NULL DEFAULT FALSE,
    ADD COLUMN settled_date    DATE,
    -- Emanet kasası çekin şirketinde olmalı (MX5 D9 deseni; NULL → denetlenmez, MATCH SIMPLE)
    ADD CONSTRAINT instrument_custody_company_fk
        FOREIGN KEY (custody_fund_id, company_id) REFERENCES fund_account (id, company_id),
    ADD CONSTRAINT instrument_note_type_ck CHECK (
        note_type IS NULL OR (kind = 'NOTE' AND note_type IN ('PLAIN', 'ORDER', 'BOND'))),
    ADD CONSTRAINT instrument_collateral_ck CHECK (is_collateral = FALSE OR kind = 'NOTE'),
    ADD CONSTRAINT instrument_dates_ck CHECK (issue_date IS NULL OR issue_date <= due_date);

-- 3. Hareket satırının fonu: AT_BANK/COLLECTED/PAID'de banka, COLLECTED_TO_CASH'te kasa,
--    PORTFOLIO'da (emanet) kasa. Mevcut satırlar NULL kalır.
ALTER TABLE instrument_movement
    ADD COLUMN fund_account_id UUID REFERENCES fund_account (id);

-- 4. Numara tekilliği: iptal/iade edilen çekin numarası yeniden kullanılabilir (düzeltme; OK-12.3-5).
--    Koşul daraldığı için dolu veride ihlal oluşmaz. Kolon sırası korunur (CompanyMigrationIT G-9).
DROP INDEX instrument_number_uq;
CREATE UNIQUE INDEX instrument_number_uq
    ON instrument (company_id, kind, direction, number, COALESCE(bank_name, ''))
    WHERE deleted = FALSE AND status NOT IN ('CANCELLED', 'RETURNED');

-- 5. Liste/rapor indeksleri (vade aralığı + cari süzgeci)
CREATE INDEX instrument_due_idx ON instrument (company_id, direction, kind, due_date) WHERE deleted = FALSE;
CREATE INDEX instrument_account_idx ON instrument (account_id) WHERE deleted = FALSE;
CREATE INDEX instrument_movement_fund_idx ON instrument_movement (fund_account_id)
    WHERE fund_account_id IS NOT NULL;
```

Notlar:
- **`is_collateral`.** Kolon eklenir ama 12.3'te yazılmaz (OK-12.3-7).
- **`settled_date`.** `COLLECTED`, `COLLECTED_TO_CASH` ve `PAID` geçişinde hareket tarihiyle yazılır. Geri doldurma **yok**: eski tahsil edilmiş çekte NULL kalır, rapor `NULL` için "-" gösterir.

### 1.2 `MIG/V38__check_book.sql` (Z09)

```sql
-- Z09 · Faz 12.3 · MX3 §2.3, §4 (V23 taslağının yerine) · 12.3_TASARIM §1.2
-- Çek koçanı ve yaprakları. Şirket kapsamı bileşik FK ile (MX5). Yaprak → çek bağı yalnız
-- instrument.check_leaf_id üzerinden (döngüsel FK yok).

CREATE TABLE check_book (
    id              UUID PRIMARY KEY,
    company_id      UUID         NOT NULL REFERENCES company (id),
    branch_id       UUID         NOT NULL,
    fund_account_id UUID         NOT NULL,
    serial_no       VARCHAR(50)  NOT NULL,
    bank_code       CHAR(4),
    branch_code     CHAR(4),
    start_number    VARCHAR(7)   NOT NULL,
    end_number      VARCHAR(7)   NOT NULL,
    leaf_count      INTEGER      NOT NULL,
    created_by      VARCHAR(254) NOT NULL,
    created_at      TIMESTAMPTZ  NOT NULL,
    updated_by      VARCHAR(254) NOT NULL,
    updated_at      TIMESTAMPTZ  NOT NULL,
    deleted         BOOLEAN      NOT NULL DEFAULT FALSE,
    CONSTRAINT check_book_id_company_uq UNIQUE (id, company_id),
    CONSTRAINT check_book_branch_company_fk
        FOREIGN KEY (branch_id, company_id) REFERENCES branch (id, company_id),
    CONSTRAINT check_book_fund_company_fk
        FOREIGN KEY (fund_account_id, company_id) REFERENCES fund_account (id, company_id),
    CONSTRAINT check_book_numbers_ck CHECK (
        start_number ~ '^[0-9]{7}$' AND end_number ~ '^[0-9]{7}$' AND start_number <= end_number),
    CONSTRAINT check_book_codes_ck CHECK (
        (bank_code IS NULL OR bank_code ~ '^[0-9]{4}$')
        AND (branch_code IS NULL OR branch_code ~ '^[0-9]{4}$')),
    CONSTRAINT check_book_leaf_count_ck CHECK (leaf_count BETWEEN 1 AND 1000)
);
CREATE UNIQUE INDEX check_book_serial_uq ON check_book (fund_account_id, serial_no) WHERE deleted = FALSE;
CREATE INDEX check_book_company_idx ON check_book (company_id, branch_id) WHERE deleted = FALSE;

CREATE TABLE check_leaf (
    id              UUID PRIMARY KEY,
    company_id      UUID         NOT NULL,
    check_book_id   UUID         NOT NULL,
    fund_account_id UUID         NOT NULL,
    leaf_no         INTEGER      NOT NULL,
    number          VARCHAR(7)   NOT NULL,
    micr_code       VARCHAR(30),
    status          VARCHAR(10)  NOT NULL DEFAULT 'UNUSED',
    used_date       DATE,
    void_reason     VARCHAR(500),
    created_by      VARCHAR(254) NOT NULL,
    created_at      TIMESTAMPTZ  NOT NULL,
    updated_by      VARCHAR(254) NOT NULL,
    updated_at      TIMESTAMPTZ  NOT NULL,
    deleted         BOOLEAN      NOT NULL DEFAULT FALSE,
    CONSTRAINT check_leaf_id_company_uq UNIQUE (id, company_id),
    CONSTRAINT check_leaf_book_company_fk
        FOREIGN KEY (check_book_id, company_id) REFERENCES check_book (id, company_id),
    CONSTRAINT check_leaf_fund_company_fk
        FOREIGN KEY (fund_account_id, company_id) REFERENCES fund_account (id, company_id),
    CONSTRAINT check_leaf_number_ck CHECK (number ~ '^[0-9]{7}$'),
    CONSTRAINT check_leaf_leaf_no_ck CHECK (leaf_no >= 1),
    CONSTRAINT check_leaf_status_ck CHECK (status IN ('UNUSED', 'USED', 'VOID')),
    CONSTRAINT check_leaf_used_ck CHECK (status <> 'USED' OR used_date IS NOT NULL)
);
-- Aynı banka hesabında bir numara tek yaprak (ZTO CBC:208-224 denetimi)
CREATE UNIQUE INDEX check_leaf_number_uq ON check_leaf (fund_account_id, number) WHERE deleted = FALSE;
CREATE INDEX check_leaf_book_idx ON check_leaf (check_book_id, leaf_no);
CREATE INDEX check_leaf_status_idx ON check_leaf (fund_account_id, status) WHERE deleted = FALSE;

-- Çek → yaprak (tek yönlü). Bir yaprak en çok bir etkin (iptal edilmemiş) çekte.
ALTER TABLE instrument
    ADD COLUMN check_leaf_id UUID,
    ADD CONSTRAINT instrument_check_leaf_fk
        FOREIGN KEY (check_leaf_id, company_id) REFERENCES check_leaf (id, company_id);
CREATE UNIQUE INDEX instrument_check_leaf_uq ON instrument (check_leaf_id)
    WHERE check_leaf_id IS NOT NULL AND deleted = FALSE AND status <> 'CANCELLED';
```

### 3.2 `InstrumentService` değişiklikleri (B2)

**`register(NewInstrument data, direction, accountId, branchId, money, date)`** genişler:
1. Kurucudan sonra `instrument.withDetails(data.issueDate(), trim(data.bankBranch()), trim(data.drawerName()), trim(data.description()), data.noteType())`.
2. **Yaprak** (`data.checkLeafId() != null`). Doğrulama SS'de (§3.3); burada şu sırayla işlenir:
   - `leaves.findForUpdate(id)`
   - durum `UNUSED` değilse 409 `CHECK_LEAF_USED`
   - `leaf.use(date)`
   - `instrument.attachLeaf(leaf.getId())`
3. **Emanet.** `direction == RECEIVED && initial == PORTFOLIO && data.custodyFundId() != null` ise:
   - `requireFund(instrument, custodyFundId, FundKind.CASH)` (mevcut metot; tür, para birimi, şirket),
   - `FundService.requireActive`,
   - `instrument.assignCustody(id)`,
   - ilk hareketin `fund_account_id`'si = kasa.
4. **İlk hareketin fonu.**
   - Verilen çekte `fundAccountId` (çekin çekildiği banka) harekete **yazılmaz**; para hareketi değildir.
   - `AT_BANK` hareketine banka yazılır.

**`transition(id, request)`.** Sıra mevcut koddaki gibidir: `lock → requireVisible → ensureAllowed → assignFundIfNeeded → record → applyEffects`. Eklemeler:
- **Tür ayrımı.** `PROTESTED` yalnız NOTE'ta, `BOUNCED` yalnız CHECK'te (§3.1 tablosu).
- **`assignFundIfNeeded`.**
  - `COLLECTED`: çek `AT_BANK` ise mevcut banka kalır. `fundAccountId` verilmişse ve farklıysa 400 `FUND_MISMATCH` ("Çek başka bankada."). `PORTFOLIO`'dan geliyorsa `fundAccountId` zorunludur (BANK).
  - `AT_BANK`, `PAID`: BANK.
  - `COLLECTED_TO_CASH`: CASH (mevcut).
  - `PORTFOLIO` (`AT_BANK`'tan): `clearFund()`. `request.custodyFundId()` verilmişse CASH denetimi ve `assignCustody`. Sunucuda zorunlu değildir; ZTO ekranı zorunlu tutar.
  - Diğer hedeflerde `fundAccountId` verilirse yok sayılır (mevcut davranış).
- **`record(...)`.** Harekete `fund_account_id` yazılır:
  - `AT_BANK`, `COLLECTED`, `COLLECTED_TO_CASH`, `PAID`: atanmış fon;
  - `PORTFOLIO`: emanet kasası.
- **`applyEffects`.**
  - `COLLECTED`, `COLLECTED_TO_CASH`: fon IN + `markSettled(date)`.
  - `PAID`: fon OUT + `markSettled(date)`.
  - `BOUNCED`, `PROTESTED`: `applyBounce` (mevcut). `postAccount` açıklaması "Karşılıksız çek/senet {no}" ya da `PROTESTED` için "Protestolu senet {no}".
  - `RETURNED`: `postAccount(accountId, DEBIT, …, SOURCE_MOVEMENT, movementId, request)`, açıklama "Çek/senet iadesi {no}".
  - `COLLATERAL`, `PORTFOLIO`: etki yok.
  - Hedef `PORTFOLIO` değilse `clearCustody()`.
- **İzin denetimi.** Transition ucu bugünkü izniyle (`POST` = `FINANCE_PAYMENT_CREATE`) kalır.
- **Personel carisi.** Çekin carisi personelse ve kullanıcının `FINANCE_EMPLOYEE_VIEW` izni yoksa 404 `INSTRUMENT_NOT_FOUND` döner (12.2a OK-12.2a-8 deseni; `AccountAccess.requireReadable` 404 fırlatır). Bu denetim tüm tekil çek uçlarına uygulanır: `requireReadable(instrument)` yardımcısı ile; yeni ve mevcut transition, history, detail, PATCH, custody, dosyalar.

**`history(id)`.** Çek yoksa 404 `INSTRUMENT_NOT_FOUND` döner (bugün boş liste dönüyor). Ardından `requireVisible` ve `requireReadable`.

**Yeni metotlar:**
- **`updateDetails(UUID id, InstrumentUpdateRequest r)`** (PATCH). Akış: `lock → requireVisible → requireReadable`. Ardından:
  1. Durum `CANCELLED`/`RETURNED` ise 409 `INSTRUMENT_NOT_EDITABLE` ("İptal/iade edilmiş çek/senet düzenlenemez.").
  2. `number` değişiyorsa:
     - yaprak bağlıysa 409 `INSTRUMENT_LEAF_NUMBER_LOCKED` ("Koçandan seçilen çekin numarası değiştirilemez.");
     - CHECK'te `^\d{7}$` sağlanmıyorsa 400 `CHECK_NUMBER_INVALID`;
     - `existsActiveNumber(..., excludeId=id)` doluysa 409 `INSTRUMENT_NUMBER_TAKEN`.
  3. `dueDate` yalnız `PORTFOLIO`, `AT_BANK`, `ISSUED`, `COLLATERAL` durumunda değişebilir; aksi halde 409 `INSTRUMENT_NOT_EDITABLE` (OK-12.3-14).
  4. `issueDate ≤ dueDate` sağlanmazsa 400 `INSTRUMENT_DATES_INVALID`.
  5. `noteType` yalnız NOTE'ta; CHECK'te gönderilirse 400 `NOTE_TYPE_INVALID`.
  6. Alanlar yazılır. Yalnız değişen alan adları denetim kaydına yazılır: `AuditEvent.INSTRUMENT_UPDATED`, hedef `INSTRUMENT:<id>`, `fields=number,bankName`. Değerler yazılmaz (KVKK).
  7. **Defter kaydı ve hareket satırı yazılmaz.**

  PATCH semantiği: istekte bulunan (null olmayan) alanlar değişir; boş string → NULL (yalnız `bankBranch`, `drawerName`, `description`). `number`, `dueDate` NULL olamaz.
- **`moveCustody(UUID id, InstrumentCustodyRequest r)`** (PUT). Akış: `lock → requireVisible → requireReadable`.
  - Yalnız `RECEIVED` + `PORTFOLIO`; aksi halde 409 `INSTRUMENT_INVALID_TRANSITION`.
  - `r.custodyFundId()` null değilse CASH, aktif, aynı şirket, aynı para birimi.
  - Hareket satırı yazılır: `PORTFOLIO→PORTFOLIO`, `fund_account_id`, `note = r.note() ?? "Kasa değişikliği"`, `date = r.date()`.
  - Denetim kaydı `INSTRUMENT_CUSTODY_MOVED`.
  - Aynı kasaya tekrar istek gelirse değişiklik ve hareket yazılmaz (idempotent); 200 döner.
- **`lockForSettlement(UUID id)`**: `findForUpdate`, bulunamazsa 404.
- **`cancelForSettlement(Instrument i, LocalDate date, String note, boolean releaseLeaf)`**:
  1. Hareket `from → CANCELLED`, `date`, `note`;
  2. `clearCustody()`;
  3. `checkLeafId != null` ise yaprak `findForUpdate`: `releaseLeaf` ise `release()`, değilse `voidLeaf("Ödeme iptali")`.
  - Defter kaydı yazmaz; köken kaydın tersi SS'dedir.
- **`undoEndorsement(Instrument i, LocalDate date, String note)`**: `ENDORSED → PORTFOLIO` hareketi (`note` ya da "Ciro iptali"), ardından `clearEndorsement()`. Defter yazmaz.

### 3.3 `SettlementService.validateInstrument` eklemeleri (B2)

Aşağıdaki denetimler `preview == false` iken uygulanır. Önizlemede ön yüz yer tutucu numara gönderir (12.2a F-12.2-R4); orada yalnız 5. ve 6. maddeler çalışır.

**Düzeltme bağlamı (Rev 1 F1).** İmza `validate(type, request, preview, CorrectionContext ctx)` ve `validateInstrument(type, request, companyId, ctx)` olur. Yeni kayıtta ve önizlemede `ctx = null`'dur. `correct()` (§3.5) eski kayıt çekli bir **köken** kayıtsa `ctx = new CorrectionContext(oldInstrumentId, oldCheckLeafId, oldNumber, oldFundAccountId)` geçirir (SS içinde `private record`). Neden: `correct()` `validate`'i eski kaydın tersinden önce çağırır (SS:587). O anda eski çek hâlâ etkin, yaprağı hâlâ `USED`'dır. Bağlam olmasa "aynı çekin tutarını/tarihini düzelt" akışı her zaman 409 alırdı. Bağlam yalnız aşağıdaki 2–4. maddeleri gevşetir; kilit altındaki asıl denetim yine `register()`'dadır. O noktada eski çek `CANCELLED`, yaprağı `UNUSED` olmuştur (§3.5 sıra kuralı).

1. **Numara biçimi.** `kind == CHECK` iken `number` `^\d{7}$` olmalıdır; değilse 400 `CHECK_NUMBER_INVALID` ("Çek numarası 7 haneli sayısal değer olmalıdır."). NOTE serbesttir (≤ 50). `NewInstrument.number` DTO'da `@Size(max=50)` kalır.
2. **Numara tekilliği.** `existsActiveNumber(companyId, kind, direction, number, bankName, ctx?.oldInstrumentId)` doluysa 409 `INSTRUMENT_NUMBER_TAKEN`. Durum "Bu çek numarası zaten kullanılıyor!" iletisi ve `details = ["status=<durum>"]` ile döner. DB indeksi ikinci savunmadır.
3. **Yaprak.** `checkLeafId` yalnız şu koşulların hepsinde kabul edilir: `PAYMENT`, `kind == CHECK`, yeni çek (ciro değil), `fundAccountId != null`. Aksi halde 400 `CHECK_LEAF_INVALID`. Yaprak bulunur (`findById`, `deleted=false`; yoksa 404 `CHECK_LEAF_NOT_FOUND`) ve şu koşullar aranır:
   - `leaf.fundAccountId == data.fundAccountId` ve `leaf.number == data.number`, değilse 422 `CHECK_LEAF_MISMATCH`;
   - `leaf.status == UNUSED` ya da `leaf.id == ctx?.oldCheckLeafId` (düzeltmede eski yaprak `USED` olsa da kabul), değilse 409 `CHECK_LEAF_USED` ("Bu çek zaten kullanılmış (ödemesi mevcut), tekrar kullanılamaz.").
   - Kilitli yeniden denetim `register`'dadır.
4. **Elle girilen numara.** Verilen çekte (`ISSUED` + CHECK) yaprak yokken `fundAccountId` doluysa ve `leaves.findByFundAccountIdAndNumberAndDeletedFalse(fundAccountId, number)` bir yaprak bulursa 409 `CHECK_NUMBER_IN_CHECK_BOOK` döner ("Bu çek numarası koçan yaprağı olarak kayıtlı — manuel olarak kullanılamaz, lütfen koçandan seçiniz."). Ayrıntı `details = ["leafId=…", "leafStatus=…"]`. CLG:57-85 kuralı sunucuda uygulanmış olur.
   - **İstisna (düzeltme):** eski çek de yapraksızsa (`ctx.oldCheckLeafId == null`) ve numara ile fon eskisiyle aynıysa denetim atlanır. Bu durumda yaprak, eski çek elle girildikten sonra açılan bir koçandan gelmiştir.
   - Eski çek yapraklıysa istisna yoktur; ön yüz `checkLeafId`'yi doldurur (§5.10).
5. **Tarih sırası.** `issueDate != null && issueDate > dueDate` ise 400 `INSTRUMENT_DATES_INVALID` ("Vade tarihi, keşide tarihinden önce olamaz!").
6. **Emanet kasası.** `custodyFundId` yalnız `COLLECTION` + ilk durum `PORTFOLIO` (ya da null) iken kabul edilir; aksi halde 400 `INSTRUMENT_CUSTODY_INVALID`. Sonra `checkFund(funds.findVisible(id), FundKind.CASH, currency, companyId)` + `FundService.requireActive`. Mevcut "Portföydeki çek/senede banka hesabı seçilemez" kuralı yalnız `fundAccountId` için kalır.
7. **Senet türü.** `noteType` yalnız NOTE'ta; CHECK'te 400 `NOTE_TYPE_INVALID`. NOTE'ta `noteType` null ise `PLAIN` yazılır (ZTO varsayılanı "Adi Senet").
8. **Keşideci adı.** `drawerName` yalnız `RECEIVED`'da anlamlıdır; `ISSUED`'da yok sayılır, NULL yazılır.

### 3.4 Çekli kaydın iptali — `doReverse` (B2)

**`requireReversibleKind`.** CHECK koşulu kaldırılır; yalnız plan denetimi kalır. Metot adı korunur, Javadoc güncellenir.

**Yeni akış** (USER, INTERCOMPANY, MANAGED kipleri aynı; çekli kayıt bugün yalnız USER kipinde gelir):
1. `settlement` kilitsiz okunur, `requireVisible`, `requireSettlementReadable`, REVERSED ise döner (idempotent; mevcut).
2. `requireReversibleKind(settlement)`.
3. **Ön denetim** (kilitsiz, hızlı 409): `method == CHECK` ise `instruments.findById(settlement.instrumentId)` ve `requireInstrumentReversible(settlement, instrument)`.
4. `requireReverseDate` (mevcut; USER).
5. Fon kilidi (mevcut; çekli kayıtta fon yok).
6. `entityManager.refresh(settlement, PESSIMISTIC_WRITE)`; REVERSED ise döner.
7. `requireUnlinked(settlement, mode)` (mevcut; cari taşıma `TRANSACTION_TRANSFERRED` dahil).
8. **Yeni (Rev 1 F2):** `method == CHECK` ise sıra şöyledir:
   - önce `ledger.lockSource(SOURCE_SETTLEMENT, settlement.id)`: kaydın cari hareketi `FOR UPDATE` kilitlenir;
   - sonra `Instrument i = instruments.lockForSettlement(settlement.instrumentId)`;
   - ardından kilit altında yeniden `requireInstrumentReversible(settlement, i)`.

   Cari taşıma (`AccountTransferService:239-268`) kilitleri cari → `account_transaction` → `instrument` sırasıyla alır. İptal de aynı sırayı izler, böylece 40P01 döngüsü oluşmaz. `LedgerService.lockSource(String sourceType, UUID sourceId)` yeni ve salt kilit alan bir metottur: `findBySourceTypeAndSourceId` + `findForUpdate`, satır yoksa hiçbir şey yapmaz. Defter yazmaz. Sonradan `reverse()` içindeki `findForUpdate` aynı işlemde yeniden girer, ek bekleme olmaz.
9. `reverseLedgers(settlement, date, reason, defaultText)` (mevcut).
10. **Yeni:**
    - Köken kayıtsa `instruments.cancelForSettlement(i, date, textOf(reason, defaultText), false)`: yaprak `VOID` olur (kağıt yazılmış sayılır).
    - Ciro kaydıysa `instruments.undoEndorsement(i, date, "Ciro iptali")`.
11. Denetim kaydı (mevcut).

**`requireInstrumentReversible(Settlement s, Instrument i)`** → `InstrumentRules.settlementReversible(s.type, i.direction, i.status, i.endorsedAccountId, s.accountId)`. Doğru olduğu durumlar:
- köken + `RECEIVED`: `status ∈ {PORTFOLIO, AT_BANK}` (AT_BANK fon yazmadığı için iptal güvenlidir);
- köken + `ISSUED`: `status == ISSUED`;
- ciro (`PAYMENT` + `RECEIVED`): `status == ENDORSED && endorsedAccountId == s.accountId`.

Yanlışsa 409 `SETTLEMENT_CHECK_NOT_REVERSIBLE`:
- ileti: "Çek/senet işlem gördü (durum: {etiket}); önce çekin durumunu geri alacak işlemi yapın ya da çek ekranından ilerleyin.";
- `details = ["instrumentStatus=<durum>", "instrumentId=<id>"]`.

**Sonuç notları:**
- İptal edilen köken çekin numarası `instrument_number_uq` dışına çıkar; aynı numara yeniden girilebilir.
- AT_BANK çekte iptal sonrası `fund_account_id` dolu kalır; `CANCELLED` durumu raporlarda dışlanır.

### 3.5 Çekli kaydın düzeltmesi — `correct` (B2)

- **Engel kalkar.** SS:556-559 `CORRECTION_METHOD_INVALID` kaldırılır; yeni kayıt `CASH`, `BANK` ya da `CHECK` olabilir. Kod adı katalogda "kullanılmıyor" olarak kalmaz, silinir. FE eşlemesi varsa FE-3 kaldırır.
- **`requireCorrectable(old)`.** Mevcut denetimler + `old.method == CHECK` ise ön denetim (§3.4 adım 3).
- **Kilit sırası** (§3.10):
  1. yeni cari FOR SHARE;
  2. fonlar (`lockFunds(old.fund, replacement.fund)`; çekli kayıtta null atlanır);
  3. eski settlement FOR UPDATE;
  4. **eski kaydın cari hareketi FOR UPDATE** (`ledger.lockSource`; `old.method == CHECK`; Rev 1 F2);
  5. **eski çek FOR UPDATE** (`old.method == CHECK`);
  6. `requireInstrumentReversible` yeniden denetlenir.

  Yeni kaydın ciro çeki `endorse()` içinde, yaprak `register()` içinde kilitlenir.
- **Doğrulama bağlamı (Rev 1 F1).** SS:587'deki `validate(type, replacement, false, ctx)` kilitlerden sonra, tersten önce kalır (12.2a sırası; 400 hataları hiçbir şey yazılmadan döner).
  - **Köken çekli eski kayıt:** `ctx` eski çekin kimliği, yaprağı, numarası ve fonuyla kurulur (§3.3). Aynı numara ve aynı yaprakla düzeltme bu ön denetimden geçer.
  - **Ciro eski kayıt:** `ctx = null`. Yeni ciro isteği `instrument == null` olduğu için `validateInstrument` çalışmaz. `endorse()` çeki ters işlemden sonra kilitler; o anda çek `PORTFOLIO`'dadır.
  - **Reddedilen alternatif:** `validate`'i tersten sonraya taşımak. Bu, 12.2a hata sırasını ve kilit süresini değiştirirdi.
- **Sıra kuralı.** `old.method == CHECK || replacement.method == CHECK` ise iki türde de önce eski kaydın tersi yazılır:
  1. `reverseLedgers(old, old.settlementDate, reason, text)`;
  2. köken için `cancelForSettlement(oldInstrument, old.settlementDate, text, true)` (yaprak `UNUSED`), ciro için `undoEndorsement(…)`;
  3. `entityManager.flush()`;
  4. `confirm(...)`;
  5. `insert(...)`;
  6. `allocations.save(...)`.

  Gerekçe: numara indeksi ve yaprak çakışması önlenir. Ciro düzeltmesinde aynı çek önce `PORTFOLIO`'ya döner, sonra yeniden `ENDORSED` olur. Çek içermeyen kayıtta 12.2a sırası (ödemede ters → yeni; tahsilatta yeni → ters) **aynen** kalır.
- **Kapsam.** Aynı şirket kuralı ve `COMPANY_MISMATCH` (mevcut) geçerlidir.
- **Çek alanlarının taşınması.** Düzeltme isteğinde `replacement.instrument` tam gönderilir; sunucu eski çekten alan kopyalamaz. Ön yüz eski çekin alanlarını forma doldurur (§5.10).

### 3.6 `CheckBookService` (B3, yeni; `BE/finance/service/CheckBookService.java`)

**`create(CheckBookRequest r)`** (`FINANCE_MANAGE`):
1. `FundAccount f = funds.findVisible(r.fundAccountId())` (kapsam 403/404), `FundService.requireActive(f)`; `f.kind != BANK` ise 400 `FUND_KIND_MISMATCH` ("Lütfen banka hesabı seçiniz!").
2. `serialNo` kırpılır, 1–50 karakter; `startNumber`/`endNumber` `^\d{7}$`; `bankCode`/`branchCode` ikisi birlikte boş ya da ikisi de `^\d{4}$`. Hatalarda 400 `CHECK_BOOK_INVALID`; `details` alan adı (`field=startNumber`); ZTO iletileri §5.7.
3. `start ≤ end` ve `end − start + 1 ≤ 1000`; değilse 400 `CHECK_BOOK_RANGE_INVALID` ("Bir koçanda en çok 1000 yaprak olabilir.").
4. `fundAccounts.findForUpdate(f.id)`: aynı fonda eşzamanlı iki koçan sıraya girer.
5. Aynı fonda aynı `serialNo` varsa 409 `CHECK_BOOK_SERIAL_TAKEN`.
6. `Set<String> existing = leaves.findNumbersByFundAccountId(f.id)`. `n = start..end` için:
   - `number = String.format("%07d", n)` (ZTO hatası (k) düzeltilir: ZTO `i.ToString()` baştaki sıfırı düşürür);
   - `existing.contains(number)` ise numara `skipped` listesine girer (ZTO CBC:208-224 deseni);
   - değilse yaprak oluşturulur: `leafNo = n − start + 1`, MICR = `bankCode != null ? "c" + bankCode + branchCode + String.format("%08d", n) : null` (CBC:228-232), `status = UNUSED`.
7. Oluşan yaprak sayısı 0 ise 409 `CHECK_BOOK_EMPTY` ("Girilen aralıktaki tüm çek numaraları zaten kayıtlı."). Aksi halde `check_book` kaydı (`leafCount` = oluşan adet, `companyId`/`branchId` fondan) ve yapraklar yazılır (`saveAll`).
8. Denetim kaydı: `CHECK_BOOK_CREATED`, hedef `CHECK_BOOK:<id>`, `leaves=N,skipped=M`.
9. Yanıt: `CheckBookCreatedResponse {book, createdCount, skippedNumbers}`.

**`voidLeaf(UUID leafId, CheckLeafVoidRequest r)`** (`FINANCE_MANAGE`):
1. `leaves.findForUpdate` (yoksa 404 `CHECK_LEAF_NOT_FOUND`), `scope.requireVisible(book.branchId)`.
2. `VOID` ise idempotent: 200 ve aynı yaprak döner.
3. `USED` ise `instruments.findByCheckLeafIdAndDeletedFalse` içinde `CANCELLED` olmayan çek varsa 409 `CHECK_LEAF_IN_USE` ("Bu yaprak etkin bir çekte kullanılıyor; önce ödemeyi iptal edin.").
4. `leaf.voidLeaf(r.reason())`, denetim kaydı `CHECK_LEAF_VOIDED`.

**`deleteLeaf(UUID leafId)`** (`FINANCE_MANAGE`):
- Yalnız `UNUSED`; aksi halde 409 `CHECK_LEAF_NOT_DELETABLE` ("Yalnız kullanılmamış yaprak silinebilir.").
- `softDelete()`, denetim kaydı `CHECK_LEAF_DELETED`. Koçanın `leafCount` alanı değişmez (tarihsel).

**Okumalar** (`FINANCE_VIEW`; `CheckBookQueryRepository`): listeler, yaprak listesi, lookup (§4).

### 3.10 Kilit sırası ve eşzamanlılık

12.2a §3.11 sırası genişler: (1) cari FOR SHARE → (2) fonlar (id sırası) → (3) settlement → **(3b) settlement'ın cari hareketi (`account_transaction` FOR UPDATE, `ledger.lockSource`)** → **(4) çek (`instrument` FOR UPDATE)** → **(5) yaprak (`check_leaf` FOR UPDATE)** → (6) eşleştirme hedefleri → (7) belge serisi → defter yazımı (kart kilidi `LedgerService` içinde). (3b)→(4), cari taşımanın `account_transaction → instrument` sırasıyla aynıdır (`AccountTransferService:239-268`).

| Yol | Sıra |
|---|---|
| `createByUser` (çekli) | cari → fon (yok) → (ciro) çek `endorse.lock` → (yaprak) `register` içinde yaprak → defter |
| `transition` | çek → fon (`FundLedgerService` içi) → defter. Settlement kilidi almaz. |
| `doReverse` (çekli) | settlement → cari hareketi (`lockSource`) → çek → yaprak (`cancelForSettlement`) → defter tersi |
| `correct` (çekli) | cari → fonlar → eski settlement → eski cari hareketi (`lockSource`) → eski çek → (yaprak release) → yeni ciro çeki / yeni yaprak → defter |
| `AccountTransferService.transfer` (mevcut) | cari kartları FOR NO KEY UPDATE → hareketler → çekler |
| `voidLeaf` | yaprak → (çek **kilitsiz** okunur; `CANCELLED` son durumdur) |
| `CheckBookService.create` | fon FOR UPDATE → yapraklar (ekleme) |
| PATCH / custody | çek |

12.3'ün eklediği yollarda döngü yoktur:
- Çeki kilitleyen hiçbir yol sonradan settlement kilidini almaz.
- Çekli iptal ve düzeltme, kaydın cari hareketini çekten **önce** kilitler. Böylece cari taşımayla aynı `account_transaction → instrument` sırasını izler (Rev 1 F2). Bu kilit olmasaydı `doReverse` çek → hareket sırasıyla kilitlerdi (`LedgerService:160`). Bu, 12.3'ün yeni açtığı çekli iptal yolunda taşımanın tersi olurdu.
- Yaprak her zaman çekten sonra kilitlenir; `voidLeaf` çeki kilitlemez.
- 12.3 öncesinden kalan tek ters sıra `transition` ∥ taşımadır (R-1).

**Eşzamanlılık IT'leri** (`CyclicBarrier`; hiçbirinde 40P01 ya da 500 olmamalı):
- aynı PORTFOLIO tahsilat çekinde "tahsilat iptali ∥ `PORTFOLIO→COLLECTED`": biri başarılı, diğeri 409 (`SETTLEMENT_CHECK_NOT_REVERSIBLE` ya da `INSTRUMENT_INVALID_TRANSITION`);
- aynı yaprakla iki ödeme: biri 201, diğeri 409 `CHECK_LEAF_USED`;
- aynı PORTFOLIO çekli tahsilatta "tahsilat iptali ∥ cari taşıma (o tahsilatın hareketi seçili)": biri başarılı, diğeri 409 (`TRANSACTION_TRANSFERRED` ya da taşımanın hareket/çek uygunluk kodu) (Rev 1 F2);
- aynı fonda çakışan aralıkla iki koçan: ikisi de başarılı, ikincisi çakışanları `skippedNumbers`'a yazar.
